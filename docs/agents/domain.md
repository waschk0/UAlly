# Domain Docs

Before exploring, read `GLOSSARY.md` at the repo root when it exists, and read ADRs under `docs/adr/` that touch the area being changed. If these files do not exist, proceed silently; create them lazily only when domain terms or decisions are actually resolved.

Use glossary vocabulary in issue titles, refactor proposals, and test names. If a needed concept is not defined, treat it as a possible `/domain-modeling` gap. If a change conflicts with an ADR, surface that conflict explicitly rather than silently overriding it.

This is a single-context repository: the glossary is `GLOSSARY.md` and ADRs live in `docs/adr/`.
